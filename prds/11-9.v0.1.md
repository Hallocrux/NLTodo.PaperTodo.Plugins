# NLTodo — Product Requirements Document

**版本：** 0.1  
**状态：** Draft  
**产品类型：** PaperTodo Web Plugin  
**项目名称：** NLTodo (Natural Language Todo)

---

## 1. 产品概述

### 1.1 产品背景

PaperTodo 提供了普通 Todo 管理和提醒功能，但用户需要通过界面手动设置提醒时间。

NLTodo 希望通过自然语言标记，降低设置 Todo 提醒的操作成本。

用户只需要在普通 Todo 文本中加入时间表达式：

```text
询问详细信息 @17tomorrow
```

NLTodo 自动识别时间表达式，并调用 PaperTodo 提供的提醒 API，为对应 Todo 设置提醒。

整个过程不需要用户离开普通 Todo 的编辑界面，也不需要额外创建插件专属的任务。

### 1.2 产品定位

NLTodo 是一个基于自然语言时间表达式的 Todo Reminder Extension。

它不负责管理 Todo，不负责实现提醒调度，也不负责替代 PaperTodo 的通知系统。

它只负责：

1. 识别 Todo 中的时间表达式。
2. 将表达式转换为绝对时间。
3. 调用 PaperTodo API 设置提醒。

### 1.3 核心设计原则

- **Native Todo First：** 用户始终使用 PaperTodo 原生 Todo。
- **Host-owned Scheduling：** 提醒调度和持久化交给 PaperTodo Host。
- **Plugin-owned Parsing：** 自然语言解析由 NLTodo 实现。
- **Minimal UI：** 不引入不必要的独立交互界面。
- **Event-driven：** 基于 Todo 事件进行处理，不通过轮询检查任务变化。
- **Idempotency：** 重复收到相同事件不能重复创建或重置提醒。

## 2. 用户需求与使用场景

### 2.1 核心用户故事

作为 PaperTodo 用户，我希望在创建或编辑普通 Todo 时，通过添加一个简单的时间表达式设置提醒，而不需要打开单独的提醒设置界面。

### 2.2 使用示例

用户输入：

```text
询问详细信息 @17tomorrow
```

系统执行：

1. PaperTodo 创建 Todo。
2. NLTodo 收到 `todo.created` 事件。
3. NLTodo 解析 `@17tomorrow`。
4. 计算目标时间。
5. 调用 `todos.setReminder`。
6. PaperTodo 保存提醒时间并负责后续调度。
7. 到期后 PaperTodo 使用内置提醒机制通知用户。

最终用户仍然看到一条普通 Todo：

```text
□ 询问详细信息 @17tomorrow
```

提醒时间由 PaperTodo 管理。

### 2.3 其他使用场景

- 创建 Todo 时直接设置提醒。
- 编辑已有 Todo，添加时间表达式。
- 修改时间表达式，自动调整提醒时间。
- 删除时间表达式，取消由 NLTodo 设置的提醒。
- PaperTodo 重启后，已有提醒仍然有效。

## 3. 时间表达式规范

### 3.1 V1 支持的语法

| 表达式 | 含义 | 示例 |
|---|---|---|
| `@17today` | 今天 17:00 | 今天下午五点 |
| `@17tomorrow` | 明天 17:00 | 明天下午五点 |
| `@09:30tomorrow` | 明天 09:30 | 明天上午九点半 |
| `@in25m` | 25 分钟后 | 25 分钟后 |
| `@in2h` | 2 小时后 | 两小时后 |
| `@2026-11-12T17:00` | 指定日期和时间 | 11 月 12 日 17:00 |

### 3.2 时间解析规则

1. 所有时间以 PaperTodo 宿主机器的本地时区解释。
2. `today` 和 `tomorrow` 表示自然日，而不是滚动的 24 小时。
3. 相对时间从首次识别表达式时开始计算。
4. 绝对时间已经过去时，不自动推迟到第二天。
5. 不支持缺少具体时间的日期表达式。
6. 一个 Todo 在 V1 中只允许出现一个有效时间表达式。
7. 多个表达式同时出现时，视为歧义，不自动设置提醒。

### 3.3 解析失败处理

以下情况不设置提醒：

- 时间格式不合法。
- 时间已经过去。
- 出现多个时间表达式。
- 日期或时间信息不完整。

解析失败时保留原始 Todo 内容，不进行破坏性修改，并记录诊断信息。

## 4. 功能需求

### FR-01：Todo 事件监听

NLTodo 必须监听 PaperTodo 提供的 Todo 事件：

- `todo.created`
- `todo.changed`
- `todo.deleted`

处理规则：

- 创建 Todo 时尝试解析。
- 修改 Todo 时检查时间表达式是否发生变化。
- 删除 Todo 时清理插件自己的状态记录。
- 不因提醒触发产生的普通状态变化重新计算相对时间。

### FR-02：时间表达式解析

NLTodo 实现独立的时间解析模块。

输入：

```text
询问详细信息 @17tomorrow
```

输出：

```json
{
  "text": "询问详细信息 @17tomorrow",
  "expression": "@17tomorrow",
  "resolvedAt": "2026-11-10T17:00:00+08:00"
}
```

解析模块不直接访问 PaperTodo，也不直接修改 Todo。

### FR-03：提醒设置

解析成功后调用：

```javascript
await papertodo.workspace.request(
    "todos.setReminder",
    {
        paperId,
        todoId,
        reminderAt
    }
);
```

提醒时间使用 ISO 8601 格式。

NLTodo 不自行创建定时器，不使用 `setTimeout` 实现长期提醒，不进行周期性轮询。

### FR-04：表达式修改

当用户修改时间表达式时：

```text
原始：
询问详细信息 @17tomorrow

修改：
询问详细信息 @18tomorrow
```

NLTodo 应重新解析并更新同一条 Todo 的提醒时间。

不得创建新的 Todo。

### FR-05：表达式删除

当用户删除时间表达式时：

```text
原始：
询问详细信息 @17tomorrow

修改：
询问详细信息
```

如果原提醒由 NLTodo 创建，且当前提醒时间仍然与 NLTodo 最后设置的时间一致，则调用 `todos.setReminder`，将 `reminderAt` 设置为 `null`。

如果用户已经手动修改了提醒时间，则不应擅自清除用户的新设置。

### FR-06：启动恢复与状态同步

NLTodo 启动时必须：

1. 读取插件持久化状态。
2. 查询现有 Todo。
3. 检查尚未处理的时间表达式。
4. 与当前 ReminderAt 进行对账。
5. 补充缺失的提醒。
6. 避免重置已经正确设置的相对时间提醒。

启动恢复不能简单地对所有 `@in25m` 重新计算，否则每次重启都会延长倒计时。

## 5. 插件架构

### 5.1 总体架构

采用 PaperTodo Web Plugin + Runtime。

```text
PaperTodo Host
│
├── Native Todo
│     │
│     └── todo.created / todo.changed
│
├── Reminder Scheduler
│     │
│     └── 负责实际提醒调度
│
└── NLTodo Plugin Provider
      │
      ├── Runtime
      │     ├── Event Listener
      │     ├── Todo Processor
      │     ├── Time Parser
      │     ├── Reminder Manager
      │     └── State Manager
      │
      └── Startup Paper
            └── Hidden
```

### 5.2 Runtime

Runtime 是插件的核心运行环境。

负责：

- 监听 Todo 事件。
- 解析时间表达式。
- 计算目标时间。
- 调用 Workspace API。
- 维护插件状态。
- 处理重复事件和异常。
- 在启动时执行状态恢复。

Runtime 独立于 Body/Mini 的 UI 生命周期。

### 5.3 Body

V1 不要求实现独立 Body UI。

未来可以增加一个可选设置界面，用于：

- 查看支持的语法。
- 查看解析失败记录。
- 设置默认时间行为。
- 查看插件运行状态。

Body 不承担后台事件监听和提醒调度职责。

### 5.4 Mini

V1 不实现 Mini。

### 5.5 Startup Paper

通过 `startupPaper.presentation: "hidden"` 创建隐藏的插件 Paper。

其作用是：

- 确保插件 Provider 有一张真实 Paper。
- 使 Runtime 能够启动。
- 不要求用户额外打开插件窗口。
- 不需要创建独立的可见 UI。

Runtime 随 Provider 生命周期运行。

## 6. Host 与 Plugin 的职责划分

| 能力 | 负责人 |
|---|---|
| Todo 数据管理 | PaperTodo Host |
| Todo 事件分发 | PaperTodo Host |
| 自然语言解析 | NLTodo |
| 时间表达式转换 | NLTodo |
| 提醒时间设置 | NLTodo 请求 Host |
| 提醒时间持久化 | PaperTodo Host |
| 提醒调度 | PaperTodo Host |
| 提醒触发状态 | PaperTodo Host |
| 默认通知展示 | PaperTodo Host |
| 自定义通知展示 | 暂不实现 |

核心数据流：

```text
User Input
    │
    ▼
Native Todo
    │
    ▼
Todo Event
    │
    ▼
NLTodo Runtime
    │
    ├── Parse Expression
    │
    ├── Resolve Timestamp
    │
    └── Set Reminder
             │
             ▼
       PaperTodo Host
             │
             ├── Persist
             ├── Schedule
             └── Notify
```

## 7. 权限与 API

### 7.1 所需权限

```json
{
  "permissions": [
    "todos.read",
    "todos.update"
  ],
  "capabilities": [
    "runtime"
  ]
}
```

### 7.2 使用的 API

| API / Event | 用途 |
|---|---|
| `papertodo.onHostEvent` | 订阅 Todo 事件 |
| `todos.list` | 启动时扫描 Todo |
| `todos.setReminder` | 设置或取消提醒 |
| Runtime State | 保存解析状态 |

V1 不需要：

- `todo.reminderUpcoming`
- `reminders.suppressDefault`
- 自定义通知机制
- 独立定时器 API

因为 V1 完全使用 PaperTodo 内置提醒。

## 8. 状态管理与可靠性

### 8.1 插件状态

Runtime State 至少保存：

```json
{
  "version": 1,
  "todos": {
    "paperId:todoId": {
      "expression": "@in25m",
      "resolvedAt": "2026-11-09T17:25:00+08:00",
      "lastAppliedReminderAt": "2026-11-09T17:25:00+08:00",
      "managedByPlugin": true
    }
  }
}
```

实际实现应使用稳定的 Paper ID 和 Todo ID 作为独立键，避免拼接造成冲突。

### 8.2 幂等性

相同 Todo、相同表达式、相同解析结果，不应重复执行提醒设置。

对于重复事件：

- 不重新计算已经解析过的相对时间。
- 不重复调用 `todos.setReminder`。
- 不重复修改 Todo 正文。

### 8.3 事件循环控制

插件自己的操作可能产生新的 Todo 事件。

因此需要：

- 使用事件订阅提供的 `excludeOwnOperations`（适用时）。
- 对每条 Todo 维护处理状态。
- 比较表达式和当前提醒时间。
- 避免重复处理和递归更新。

### 8.4 状态冲突

当用户在 PaperTodo 原生界面中手动修改提醒时间时：

- 如果时间表达式没有变化，不应重新覆盖用户设置。
- 如果表达式被删除，只能清除仍然属于 NLTodo 管理的提醒。
- 插件状态与 Host 数据不一致时，以 Host 的实际 Todo 状态为准。

## 9. 非功能需求

### NFR-01：资源占用

插件不应通过高频轮询检查 Todo。

正常情况下仅在 Todo 事件到达时执行解析。

### NFR-02：可靠性

- 支持 PaperTodo 重启后的状态恢复。
- 不因 Body 被销毁而停止监听。
- 不依赖持续存在的可见窗口。
- 不自行维护长期提醒计时器。

### NFR-03：数据安全

- 不修改与时间表达式无关的 Todo 内容。
- 不删除用户手动创建的提醒。
- 不进行未经授权的网络请求。
- 所有 Todo 修改均通过 PaperTodo Workspace API 完成。

### NFR-04：可维护性

时间解析器应与 PaperTodo API 调用逻辑解耦。

未来可以独立扩展语法，而不需要重构 Runtime 的生命周期管理。

## 10. V1 范围与非目标

### V1 必须实现

- 普通 Todo 事件监听。
- 时间表达式解析。
- 绝对时间计算。
- 相对时间计算。
- 创建和修改提醒。
- 删除表达式后清理插件管理的提醒。
- 启动时状态恢复。
- 幂等性和异常处理。
- 使用 PaperTodo 内置通知。

### V1 不实现

- 完整自然语言理解（例如「明天下午吃饭前提醒我」）。
- 多个提醒时间。
- 重复提醒。
- 日历集成。
- 自定义提醒窗口。
- 自定义声音。
- 系统级独立闹钟。
- Todo 正文的自动清理和改写。
- 多时区协同。

## 11. 验收标准

| ID | 测试场景 | 预期结果 |
|---|---|---|
| AC-01 | 新建 `询问详细信息 @17tomorrow` | 设置明天 17:00 提醒 |
| AC-02 | 新建 `任务 @in25m` | 设置 25 分钟后提醒 |
| AC-03 | 将 `@17tomorrow` 改为 `@18tomorrow` | 更新为 18:00 |
| AC-04 | 删除时间表达式 | 清除插件管理的提醒 |
| AC-05 | 修改 Todo 的无关文字 | 不重置提醒 |
| AC-06 | 重复收到同一事件 | 不重复设置提醒 |
| AC-07 | 重启 PaperTodo | 已有提醒保持有效 |
| AC-08 | Runtime 启动时发现已有标记 Todo | 能够恢复或补齐提醒 |
| AC-09 | Todo 被删除 | 清理对应插件状态 |
| AC-10 | 输入过去的时间 | 不设置提醒 |
| AC-11 | 输入多个时间表达式 | 不设置提醒并记录错误 |
| AC-12 | 用户手动修改提醒时间 | 不因无关文本修改而覆盖 |

## 12. 实施计划

### Phase 1：最小可行原型

1. 创建 Web Plugin 项目。
2. 配置 Runtime 和隐藏 Startup Paper。
3. 验证 Runtime 能否在没有 Body 的情况下启动。
4. 订阅 `todo.created`。
5. 实现 `@17tomorrow` 解析。
6. 调用 `todos.setReminder`。
7. 验证 PaperTodo 内置提醒是否正常触发。

### Phase 2：完整事件处理

1. 增加 `todo.changed`。
2. 增加 `todo.deleted`。
3. 实现表达式修改和删除处理。
4. 实现幂等性。
5. 实现 Runtime State。

### Phase 3：可靠性

1. 实现启动扫描。
2. 实现相对时间恢复。
3. 处理并发事件。
4. 处理状态冲突。
5. 完成验收测试。

### Phase 4：可选增强

- 增加 Body 设置界面。
- 增加语法帮助。
- 增加解析诊断。
- 增加更多时间表达式。
- 研究自定义提醒 UI。
