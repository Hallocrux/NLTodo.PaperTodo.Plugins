# NLTodo 自然语言时间识别 — Implementation Proposal

**版本：** draft 2（已做选型实测）
**前置：** 取代 PRD v0.2 第 3 章（`@` 标记语法）
**日期：** 2026-11-09

---

## 1. 结论

去掉 `@` 前缀，改为对整条 Todo 正文做时间识别。

**选型：`chrono-node@2.10.3`（zh + en 两个 locale），minified 77 KB。**

不是按知名度选的，是三个候选都跑同一批 20 条中文用例后选出来的。结论有两层：

1. Recognizers-Text 是三者里最重的（1.4 MB）、中文偏差最多的，**不采用**——它把"周三"解析成上周、把"11月12日"解析成 2025 年，都得靠规则层兜。
2. chrono-node 原生支持 `forwardDate`，这两个偏差直接消失；中文"半小时后"它也正确，而 Recognizers 返回的是当前时刻。

剩下的缺口（后天、一个半小时、三点）用一层薄机械规则补，不需要第二个库。

| 项 | 现在（v0.2） | 改后 |
|---|---|---|
| 触发方式 | 必须是 `@` 开头的 token | 正文自由文本 |

## 3. 选型实测

同一批用例，基准时间 `2026-11-09 19:43`（周一），三项候选各跑一遍。

### 3.1 横向对比

| 用例 | 应有 | Recognizers-Text | chrono-node | time-analyzer |
|---|---|---|---|---|
| 明天下午三点交材料 | 11-10 15:00 | ✅ | ✅ | ✅ |
| 周三上午10点开会 | **11-11** | ❌ 11-04（上周） | ✅ | ✅ |
| 11月12日17:00 | **2026**-11-12 | ❌ 2025 | ✅ | ✅ |
| 半小时后 | +30min | ❌ 返回当前时刻 | ✅ | ✅ |
| 两小时后 | +2h | ✅ | ✅ | ❌ 不识别 |
| 今晚8点 | 今天 20:00 | ✅ | ✅ | ❌ 08:00 |
| 后天 / 大后天 | +2d / +3d | ✅ | ❌ 不识别 | ✅ |
| 下周一 | 11-16 | ✅ | ✅ | ✅ |
| 三点开会 | 语义歧义 | 03:00/15:00 两候选 | ❌ 03:00 | ❌ 03:00 |
| 一个半小时后 | +90min | ❌ | ❌ | ❌ |
| 周五之前搞定 | 语义是范围 | ❌ daterange | ⚠️ 当 11-13 | ⚠️ 当 11-13 |
| 每天早上 | 应拒绝 | ❌ 当时间点 | ⚠️ 命中"早上" | ✅ 拒绝 |
| 吃饭 | 应拒绝 | ✅ | ✅ | ✅ |
| 可注入 `now` | 可测性必需 | ✅ | ✅ | ❌ 内部取 `new Date()` |
| 运行必需依赖 | 越少越好 | 0（自包含 UMD） | 1 | **194**（ANTLR 运行时） |
| Licensed | MIT | MIT | MIT | MIT |
| minified 体积 | — | **1.4 MB** | **77 KB**（zh+en 定制）<br>239 KB（全 locale） | **586 KB** |

### 3.2 结论

- **chrono-node** 胜出：中文主路径最准，`forwardDate` 原生解决"过去偏置"，77 KB，可注入基准时间，依赖只有 1 个。
- **time-analyzer** 中文覆盖也不错（唯一支持"后天/大后天"），但**不能注入 `now`**（直接取系统时间），这会让解析器无法单测；且 ANTLR 语法引擎带来 194 个依赖、586 KB。作为"中文补充"引入也不划算。
- **Recognizers-Text** 淘汰。1.4 MB 换来的中文质量还不如 77 KB 的 chrono，还得写规则修它的两个系统性偏差。

### 3.3 为什么不用两个库互补

看起来"chrono + time-analyzer 覆盖后天"很诱人，但两个库的 span 语义、时间基准、歧义策略都不同，合并结果需要仲裁层，成本远超「给 chrono 补 3 条正则」。

## 4. 识别流水线

```
text ──P0──> 归一化（中文量词/后天）──P1──> chrono ──P2──> 单段
                                                      │
                                              P3 类型/完整性闸门
                                                      │
                                              P4 维度补全
                                                      │
                                              P5 过去判定
```

### P0 — 前置归一化（补库的洞）

三处，纯正则，不改原文、只旁路计算：

| 模式 | 库的行为 | 我们的处理 |
|---|---|---|
| `后天` / `大后天` | 不识别 | 直接算 `now + 2d` / `now + 3d`，套默认时刻 |
| `N个半小时后` / `一个半小时后` | 只匹配到"半小时后" | 直接算 `now + (N*60+30)min` |
| `半小时后` / `一刻钟后` | ✅ 正确 | 放行 |

中文数字（一二三四五六七八九十两）需要一个小函数，覆盖 0–99 足够，不引 `nzh`。

### P1 — 抽取

```js
chrono.zh.parse(text, now, { forwardDate: true })
```

文化选择：含 CJK → `zh`，否则 `en`。两套 locale 都打进包里。

`forwardDate: true` 是关键：它让"周三""11月12日"自动落到未来，不需要我们算。

### P2 — 单段

**只取 `results[0]`**（chrono 按出现位置返回）。不遍历、不 fallback。

多段实测：`3天后再说，5点开会` → 返回两段，取第一段 `3天后` ✅，正是要的行为。

### P3 — 闸门

chrono 直接给 `Date` 和 `isCertain()` 元信息，比 Recognizers 的 type + values 好判断：

| 判据 | 含义 | 处理 |
|---|---|---|
| `isCertain('hour') === false` | 只有日期（`明天`、`周五`、`3天后`） | 补默认时刻 09:00 |
| `isCertain('hour') === true && isCertain('day') === false` | 只有时间（`17:00`、`三点`） | 按裸时间策略（§5.2） |
| 两者皆 true | 完整时间点 | 直接使用 |
| 无结果 | — | `no_expression`，静默忽略 |

注意：相对表达式（`半小时后`、`两小时后`）也是 `day=false`，必须先用 `后/以后/之后/in ...` 识别为相对时间，**不能**走裸时间策略。

### P4 — 补全

- 日期类 → 09:00（D-01 已定）
- 时间类 → 见 §5.2
- 相对类 → 不动

### P5 — 过去判定

最终 `<= now` → `past_time`，不设提醒，记诊断。

### 输出

```json
{
  "ok": true,
  "value": {
    "span": [0, 6],
    "matchedText": "明天下午三点",
    "resolvedAt": "2026-11-10T15:00:00+08:00",
    "kind": "datetime",
    "source": "nl"
  }
}
```

## 5. 已知缺口与策略

### 5.1 补丁覆盖（P0）

`后天`、`大后天`、`N个半小时后` —— 三处正则，约 40 行。

### 5.2 裸时间（`17:00`、`三点`）

chrono 在 `forwardDate` 下会把已过的裸时间滚到明天。已定的 D-02 是"默认不顺延"，因此：

- 设置项 `bareTimeRolloverNewDay`（默认 `false`）
- `false`：裸时间且今天已过 → `past_time` 失败
- `true`：接受 chrono 的顺延结果

### 5.3 中文"三点"的上下午歧义

chrono 与 time-analyzer 都取 03:00。中文里 `三点` 没有上下午信息，纯歧义。

**已定（D-06）：无 `上午/下午/晚上/凌晨` 限定时，1–6 点按下午理解（13:00–18:00），7–12 点按字面。**

理由：凌晨 1–6 点极少被口语省略"凌晨"，而下午 1–6 点经常说"三点"。

实现位置在 P4 补全之后、P5 之前：若 `isCertain('hour')` 为 true 但原文不含任何时段词，且小时 ∈ [1,6]，则小时 += 12。若结果已过 → 交给 P5 判 `past_time`。

### 5.4 明确不支持

- 范围：`周五之前`、`月底`（chrono 会退化成日期，语义不对，但可用）
- 周期：`每天早上`（chrono 会命中"早上"当成今天，**需要拦掉含"每"的句子**）
- 笼统：`下个月`、`年底`（不识别）

含 `每` + 时间词的句子直接判 `recurrence_unsupported`，否则会误设一次性提醒。

## 6. 状态与幂等

```json
{
  "matchedText": "明天下午三点",
  "resolvedAt": "2026-11-10T15:00:00+08:00",
  "lastAppliedReminderAt": "2026-11-10T15:00:00+08:00",
  "managedByPlugin": true,
  "source": "nl",
  "triggeredAt": null
}
```

幂等键从 `expression` 改为 **`matchedText`**：

- `matchedText` 相同 → 绝不重算 `resolvedAt`（相对时间不能被重启顺延）
- `matchedText` 变了 → 重新解析并覆盖
- `span` **不能**参与判定——正文前面插字就会变

---

## 7. 事件门控

门控仍是 `changedFields & Text`，行为不变：

- `明天` → `后天`：`matchedText` 变 → 重设
- 改无关文字：`matchedText` 不变 → 跳过
- 删掉时间词：`no_expression` → 按 FR-05 清空（仍需 `reminderAt === lastAppliedReminderAt`）

## 8. 存量数据

**已定：直接废弃 `@` 语法，不做兼容路径。**

- `@17tomorrow` 在 chrono 下同样不识别（实测）
- 存量提醒保持原样，直到用户改正文触发事件；届时 `no_expression` + 指纹匹配 → 按 FR-05 清空
- 不改写正文（NFR-03）
- README + Release 说明写清楚，版本升到 `0.2.0`

旧 `@` 文法整体删除，`prds/11-9.md` 第 3 章作废。

## 9. 测试计划

固定 `now = 2026-11-09T19:43+08:00`（周一）。

**正向（约 25 例）**
- `明天下午三点交材料`、`下周三15:00`、`今晚8点`、`12月1日`
- `20分钟后`、`两小时后`、`半小时后`、`一个半小时后`
- `周三上午10点` → **11-11**（回禁用例）
- `11月12日17:00` → **2026**（回禁用例）
- `后天`、`大后天`
- `tomorrow at 5pm`、`in 25 minutes`、`next friday`

**负向（约 10 例）**
- `吃饭`、`周五之前搞定`、`每天早上`（recurrence）、`下个月`
- `昨天`、`11月1日`（过去）
- `17:00`（裸时间，默认拒绝）
- `@17tomorrow`（存量，已废弃）

**边界**
- 空文本、纯标点、200 字长文本、多段只取第一段
