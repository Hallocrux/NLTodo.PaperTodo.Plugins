## 1. 产品概述

### 1.1 产品背景

PaperTodo 提供了普通 Todo 管理和提醒功能，但用户需要通过界面手动设置提醒时间。

NLTodo 希望通过自然语言标记，降低设置 Todo 提醒的操作成本。

用户只需要在普通 Todo 文本中加入时间表达式：

```text
询问详细信息 @17tomorrow
```

NLTodo 自动识别时间表达式，并调用 PaperTodo 提供的提醒 API，为对应 Todo 设置提醒。

整个过程不需要用户离开普通 Todo 的编辑界面，也不需要额外创建插件专属的任务。

### 1.2 产品定位

NLTodo 是一个基于自然语言时间表达式的 Todo Reminder Extension。

它不负责管理 Todo，不负责实现提醒调度，也不负责替代 PaperTodo 的通知系统。

它只负责：

1. 识别 Todo 中的时间表达式。
2. 将表达式转换为绝对时间。
3. 调用 PaperTodo API 设置提醒。

### 1.3 核心设计原则

- **Native Todo First：** 用户始终使用 PaperTodo 原生 Todo，正文不被插件改写。
- **Host-owned Scheduling：** 提醒调度和持久化交给 PaperTodo Host。
- **Plugin-owned Parsing：** 自然语言解析由 NLTodo 实现。
- **Minimal UI：** 不引入不必要的独立交互界面。
- **Event-driven：** 基于 Todo 事件进行处理，不通过轮询检查任务变化。
- **Idempotency：** 重复收到相同事件不能重复创建或重置提醒。
- **Fail Silent, Log Locally：** 解析失败不打扰用户，只写本地诊断记录。

## 2. 用户需求与使用场景

### 2.1 核心用户故事

作为 PaperTodo 用户，我希望在创建或编辑普通 Todo 时，通过添加一个简单的时间表达式设置提醒，而不需要打开单独的提醒设置界面。

### 2.2 使用示例

用户输入：

```text
询问详细信息 @17tomorrow
```

系统执行：

1. PaperTodo 创建 Todo。
2. NLTodo 收到 `todo.created` 事件。
3. NLTodo 解析 `@17tomorrow`。
4. 计算目标时间。
5. 调用 `todos.setReminder`。
6. PaperTodo 保存提醒时间并负责后续调度。
7. 到期后 PaperTodo 使用内置提醒机制通知用户。

最终用户仍然看到一条普通 Todo：

```text
□ 询问详细信息 @17tomorrow
```

提醒时间由 PaperTodo 管理，正文不被插件改写、不被清理。

### 2.3 其他使用场景

- 创建 Todo 时直接设置提醒。
- 编辑已有 Todo，添加时间表达式。
- 修改时间表达式，自动调整提醒时间。
- 删除时间表达式，取消由 NLTodo 设置的提醒。
- PaperTodo 重启后，已有提醒仍然有效。

## 3. 时间表达式规范

### 3.1 词法边界

时间表达式是一个 **token**，必须同时满足前置边界和后置边界，才进入候选集。

| 规则 | 定义 |
|---|---|
| 起始符 | `@` |
| 前置边界 | `@` 位于行首，或前一个字符是空白 / `，。！？、；：,.!?;:` |
| 后置边界 | token 结束于行尾，或下一个字符是空白 / 上述标点 |
| 特殊例外 | 后置字符是 `.` 且其后紧跟字母或数字时，**不**视为边界（避免把域名/邮箱读成表达式） |
| 字符集 | token 内只允许 `[0-9A-Za-z:+-]` |
| 最长匹配 | 同一 `@` 位置有多个可匹配形式时，取最长的一个 |

因此：

| 输入 | 结果 |
|---|---|
| `问@17tomorrow` | 不识别（前置边界不满足，`@` 前是汉字） |
| `a@17tomorrow.com` | 不识别（前置边界不满足，`@` 前是字母） |
| `@17tomorrow.com`（行首） | 不识别（`.` 后紧跟 `com`，按特殊例外不算边界） |
| `明天 @17tomorrow 提醒我` | 识别 `@17tomorrow` |
| `@17tomorrow.`（句末） | 识别 `@17tomorrow` |
| `@2026-11-12T17:00` | 优先按绝对时间形式匹配，不退化为 `@2026` |

### 3.2 候选形状过滤

只有 token 体符合下列形状之一，才视为「时间表达式候选」：

- `in<数字><单位>`
- `<HH>` / `<HH>:<MM>` 后接 `today` / `tomorrow`
- `<YYYY>-<MM>-<DD>T<HH>:<MM>`

等价的实现判据（v0.2 实现采用）：token 必须含数字，且满足以下任一条件 —— 以 `in` 开头、含 `:`、含 `-`、含 `today` / `tomorrow`。

不符合的形状（例如 `@张三`、`@所有人`、`@17`、`@2026`）**直接忽略，不进入候选集，不记录诊断**。

这条规则是「多表达式即歧义」的前置条件：只有形状合法的候选才会参与歧义判定，普通 `@提及` 不会污染结果。

### 3.3 形式化定义

```text
token      := "@" body
body       := relative | absolute | dayTime
relative   := "in" integer unit
unit       := "m" | "h" | "d"
dayTime    := timeOfDay day
timeOfDay  := HH | HH ":" MM
day        := "today" | "tomorrow"
absolute   := YYYY "-" MM "-" DD "T" HH ":" MM
```

`HH` 为 0–23 的两位整数；`MM` 为 0–59 的两位整数。`HH:MM` 与 `HH` 等价的语义为分钟补 `00`。

### 3.4 V1 支持的语法

| 表达式 | 含义 | 示例 |
|---|---|---|
| `@17today` | 今天 17:00 | 今天下午五点 |
| `@17tomorrow` | 明天 17:00 | 明天下午五点 |
| `@09:30tomorrow` | 明天 09:30 | 明天上午九点半 |
| `@in25m` | 25 分钟后 | 25 分钟后 |
| `@in2h` | 2 小时后 | 两小时后 |
| `@in1d` | 24 小时后 | 明天这个点 |
| `@2026-11-12T17:00` | 指定日期和时间 | 11 月 12 日 17:00 |

### 3.5 时间解析规则

1. 所有时间以 PaperTodo 宿主机器的本地时区解释，不做跨时区换算。
2. `today` 和 `tomorrow` 表示自然日，而不是滚动的 24 小时。
3. 相对时间（`@in*`）从**首次识别该表达式时**开始计算，结果写入状态后不再重算。
4. 绝对时间已经过去时，不自动推迟到第二天，视为解析失败。
5. 不支持缺少具体时间的日期表达式（例如 `@2026-11-12`）。
6. 一个 Todo 在 V1 中只允许出现一个有效时间表达式。
7. 出现多个**形状合法的**候选时，视为歧义，不自动设置提醒。

### 3.6 解析失败处理

以下情况不设置提醒：

- token 形状不合法（含非法数字、单位、日期分量越界）。
- 解析出的绝对时间已经过去。
- 出现多个形状合法的候选。
- 日期或时间信息不完整。

解析失败时保留原始 Todo 内容，不进行破坏性修改，并按 8.5 记录一条诊断。

## 4. 功能需求

### FR-01：Todo 事件监听

NLTodo 必须监听 PaperTodo 提供的 Todo 事件：

- `todo.created`
- `todo.changed`
- `todo.deleted`

订阅方式：

```javascript
const dispose = papertodo.onHostEvent(
  ['todo.created', 'todo.changed', 'todo.deleted'],
  handleHostEvent,
  { excludeOwnOperations: true }
);
```

`excludeOwnOperations: true` 是**必须显式声明**的选项（协议默认即为 `true`，但不得依赖默认值）。它只过滤本插件自身 operation 产生的事件，不能替代 8.3 的状态比对。

#### `todo.changed` 判定表

`TodoChangedFields` 是位标志：`Text = 1`，`Completion = 2`，`Order = 4`，`Reminder = 8`，`LinkedPaper = 16`，`LinkedPath = 32`。按下列顺序判定，命中即返回：

| 序 | 条件 | 处理 |
|---|---|---|
| 1 | `!before.reminderTriggered && after.reminderTriggered` 且不含 `Text` | 系统提醒事件，不解析，仅更新状态中的 `triggeredAt` |
| 2 | `(changedFields & Text) === 0` | 与正文无关，直接返回 |
| 3 | `before.text === after.text` | 防御性返回 |
| 4 | 解析 `after.text`，表达式与状态中记录的相同且 `resolvedAt` 未变 | 返回，不重算相对时间 |
| 5 | 解析成功且表达式新增或变更 | 调用 `todos.setReminder` 写入新时间 |
| 6 | 无候选，且状态中该 Todo `managedByPlugin === true` 且 `after.reminderAt === state.lastAppliedReminderAt` | 清空提醒（`reminderAt: null`），清除状态 |
| 7 | 无候选，但 `after.reminderAt !== state.lastAppliedReminderAt` | 用户接管，仅把状态置为 `managedByPlugin: false`，不动提醒 |
| 8 | 解析失败 | 保留原状，写诊断 |

`todo.created`：无条件解析 `todo.text`，走 5 / 8 分支。

`todo.deleted`：删除该 Todo 的状态记录，不做任何 Host 调用。

### FR-02：时间表达式解析

NLTodo 实现独立的时间解析模块。

输入：

```text
询问详细信息 @17tomorrow
```

输出：

```json
{
  "text": "询问详细信息 @17tomorrow",
  "expression": "@17tomorrow",
  "span": [9, 20],
  "resolvedAt": "2026-11-10T17:00:00+08:00",
  "kind": "dayTime"
}
```

解析模块是纯函数：

```text
parse(text, now, timeZone) -> { ok: true, value } | { ok: false, reason }
```

它不访问 PaperTodo API，不读写状态，不产生副作用。

### FR-03：提醒设置

解析成功后调用：

```javascript
await papertodo.workspace.request('todos.setReminder', {
  paperId,
  todoId,
  reminderAt   // ISO 8601 字符串；传 null 表示清空
});
```

契约（源码核对，见 7.2）：`ReminderAt` 为可空时间类型，`null` 表示清除提醒，因此 FR-05 的清空路径成立。

NLTodo 不自行创建定时器，不使用 `setTimeout` 实现长期提醒，不进行周期性轮询。

### FR-04：表达式修改

当用户修改时间表达式时：

```text
原始：询问详细信息 @17tomorrow
修改：询问详细信息 @18tomorrow
```

NLTodo 应重新解析并更新同一条 Todo 的提醒时间。

不得创建新的 Todo。

即使原提醒是用户手动设置的，只要表达式发生变更，也以表达式为准覆盖（这是用户的显式意图）。

### FR-05：表达式删除

```text
原始：询问详细信息 @17tomorrow
修改：询问详细信息
```

仅当同时满足下列条件时，调用 `todos.setReminder` 将 `reminderAt` 置为 `null`：

1. 状态中该 Todo 的 `managedByPlugin === true`；
2. Host 当前的 `reminderAt` 等于状态中的 `lastAppliedReminderAt`。

任一条件不满足（用户已手动改过提醒），都不得清除，只把状态降级为 `managedByPlugin: false`。

### FR-06：启动恢复与状态同步

Runtime 启动时必须：

1. 读取 Runtime State。
2. 调用 `todos.list` 取全量快照（`{ includeBlank: false }`）。
3. 对每条 Todo 按下列对账表处理。
4. 补充缺失的提醒。
5. 清理指向已不存在 Todo 的孤儿状态。

#### 启动对账表

设 `S` = 状态中该 Todo 的记录，`R` = Host 当前 `reminderAt`。

| 情况 | 处理 |
|---|---|
| 正文有表达式，`S` 存在，`R === S.lastAppliedReminderAt` | 已正确设置，跳过。**不重算 `@in*`** |
| 正文有表达式，`S` 存在，`R == null` | 若 `S.resolvedAt` 仍在未来，按 `S.resolvedAt` 补设；否则视为过期，不补设 |
| 正文有表达式，`S` 存在，`R !== S.lastAppliedReminderAt` | 用户接管，置 `managedByPlugin: false`，不覆盖 |
| 正文有表达式，`S` 不存在 | 视为首次识别：解析并设置。`@in*` 以启动时刻为基准 |
| 正文无表达式，`S` 存在且 `managedByPlugin` | 按 FR-05 条件决定是否清空 |
| 正文无表达式，`S` 不存在 | 跳过 |
| `S` 存在但 Todo 已不存在 | 删除 `S` |

启动恢复不能简单地对所有 `@in25m` 重新计算，否则每次重启都会延长倒计时。

#### 启动竞态与重试（v0.2 实测补充）

Runtime 在 provider 出现第一张实体 Paper 时即启动，此时宿主的 Todo 模型可能尚未装载完成，`todos.list` 会返回**空数组**。空结果无法区分「工作区确实没有 Todo」与「还没加载好」，因此：

1. 空结果按 2s / 4s 退避重试，最多三次。
2. 对账过程幂等，重复执行无副作用。
3. 任何一次拿到非空列表即停止重试。

实测数据：v4.0.0-beta2 上首次调用即返回 28 条，但存在返回空的时序窗口，不能依赖单次调用。

## 5. 插件架构

### 5.1 总体架构

采用 PaperTodo Web Plugin + Runtime。

```text
PaperTodo Host
│
├── Native Todo
│     │
│     └── todo.created / todo.changed / todo.deleted
│
├── Reminder Scheduler
│     │
│     └── 负责实际提醒调度
│
└── NLTodo Plugin Provider
      │
      ├── Runtime (web/runtime.html)
      │     ├── Event Listener
      │     ├── Todo Processor
      │     ├── Time Parser
      │     ├── Reminder Manager
      │     └── State Manager
      │
      └── Startup Paper
            └── hidden（Runtime 的唯一 owner）
```

### 5.2 Manifest

完整 `plugin.json`：

```json
{
  "kind": "web",
  "id": "papertodo.nltodo",
  "name": "NLTodo",
  "description": "用 @17tomorrow 这样的标记为普通 Todo 设置提醒。",
  "version": "0.1.0",
  "apiVersion": "2.3",
  "stateVersion": 1,
  "maxPaperInstances": 1,
  "entry": "web/index.html",
  "runtime": "web/runtime.html",
  "capabilities": ["runtime"],
  "permissions": ["todos.read", "todos.update"],
  "startupPaper": {
    "enabledSetting": "autoStart",
    "instanceKey": "runtime-owner",
    "presentation": "hidden",
    "title": "NLTodo"
  },
  "settings": [
    {
      "id": "autoStart",
      "type": "boolean",
      "name": "启用 NLTodo",
      "description": "保持开启，NLTodo 才能在后台识别时间表达式。关闭后提醒不再自动设置。",
      "default": true
    }
  ]
}
```

字段约束：

- `startupPaper.enabledSetting` 必须引用同一 manifest 中一个 boolean setting，否则 manifest 无效。
- `presentation: "hidden"` 属协议 2.2 能力，`apiVersion` 必须 ≥ 2.2，本项目取 2.3。
- `id` 必须与安装目录名一致：`plugins/papertodo.nltodo/`。
- `runtime` 指向的 `web/runtime.html` 必须存在，且 `capabilities` 含 `runtime`。

### 5.3 Runtime 生命周期

Runtime 是 provider 唯一的后台 surface，不是每张 Paper 一份。

| 事件 | 结果 |
|---|---|
| 0 → 1 张实体 Paper | 启动 Runtime |
| 1 → 0 张实体 Paper | 释放 Runtime |
| 隐藏 / 折叠 / Body 重建 / Mini 回收 / 无窗口 | **不影响** Runtime |
| 启动失败 | 进入 `Failed`，不自动重试 |

**因此 hidden startup paper 是 Runtime 的唯一生命线。** 用户删除这张纸片，本次会话内 Runtime 立即释放、插件失效；下次启动时宿主按 `instanceKey` 恢复同一张纸片，功能自动恢复。此行为需写入 README 的用户提示。

Runtime 通过 `window.addEventListener('papertodo', ...)` 接收宿主的 `initialize` / `settingsChanged` / `paperEvent` 消息，不依赖 Body 页面存活。

### 5.4 Body

V1 实现一个极简 `web/index.html`，仅作 manifest `entry` 占位（宿主要求 `entry` 必须存在），不提供交互功能。

未来可扩展为设置界面：查看支持的语法、查看解析诊断、设置默认时间行为、查看运行状态。

Body 不承担后台事件监听和提醒调度职责。

### 5.5 Mini

V1 不实现 Mini。

（注：Web Mini **不支持** `onHostEvent`，将来若实现 Mini，事件订阅仍只能在 Runtime 内。）

## 6. Host 与 Plugin 的职责划分

| 能力 | 负责人 |
|---|---|
| Todo 数据管理 | PaperTodo Host |
| Todo 事件分发 | PaperTodo Host |
| 自然语言解析 | NLTodo |
| 时间表达式转换 | NLTodo |
| 提醒时间设置 | NLTodo 请求 Host |
| 提醒时间持久化 | PaperTodo Host |
| 提醒调度 | PaperTodo Host |
| 提醒触发状态 | PaperTodo Host |
| 默认通知展示 | PaperTodo Host |
| 自定义通知展示 | 暂不实现 |

核心数据流：

```text
User Input → Native Todo → Todo Event → NLTodo Runtime
                                            ├── Gate on changedFields
                                            ├── Parse Expression
                                            ├── Resolve Timestamp
                                            └── Set Reminder
                                                     │
                                              PaperTodo Host
                                                     ├── Persist
                                                     ├── Schedule
                                                     └── Notify
```

## 7. 权限与 API

### 7.1 所需权限

```json
{
  "permissions": ["todos.read", "todos.update"],
  "capabilities": ["runtime"]
}
```

`todos.setReminder` 使用 `todos.update` 权限，无需额外声明。V1 不读取 Note、不创建 Paper，因此不需要 `papers.*`、`notes.*`。

### 7.2 使用的 API 契约

源码核对来源：`PaperTodo.Plugin.Abstractions/PaperTodoHostContracts.cs`、`src/WebPluginWorkspaceRequests.cs`。

**`todos.list`**

```text
params: { paperId?: string, includeBlank?: boolean }
return: TodoSnapshot[]
```

**`todos.setReminder`**

```text
params: { paperId: string, todoId: string, reminderAt: ISO8601 | null }
```

对应契约：

```csharp
public sealed record SetTodoReminderRequest
{
    public string PaperId { get; init; } = "";
    public string TodoId { get; init; } = "";
    public DateTimeOffset? ReminderAt { get; init; }
}
```

**`TodoSnapshot` 字段**

```text
paperId, paperTitle, id, text, done, order,
linkedPaperId, linkedPath, linkedPathIsDirectory,
reminderAt, reminderTriggered
```

**`todo.changed` 事件负载**

```text
{ before: TodoSnapshot, after: TodoSnapshot,
  changedFields: number, metadata: { eventId, operationId, occurredAt, origin, sourcePluginId } }
```

**`TodoChangedFields` 位标志**

| 名称 | 值 | 含义 |
|---|---|---|
| `None` | 0 | 无变化 |
| `Text` | 1 | 正文变化 |
| `Completion` | 2 | 完成状态变化 |
| `Order` | 4 | 排序变化 |
| `Reminder` | 8 | 提醒时间变化 |
| `LinkedPaper` | 16 | 关联纸片变化 |
| `LinkedPath` | 32 | 关联路径变化 |

V1 不需要：`todo.reminderUpcoming`、`reminders.suppressDefault`、自定义通知机制、独立定时器 API。因为 V1 完全使用 PaperTodo 内置提醒。

## 8. 状态管理与可靠性

### 8.1 插件状态

Runtime State 采用两级键，避免字符串拼接冲突：

```json
{
  "version": 1,
  "todos": {
    "<paperId>": {
      "<todoId>": {
        "expression": "@in25m",
        "resolvedAt": "2026-11-09T17:25:00+08:00",
        "lastAppliedReminderAt": "2026-11-09T17:25:00+08:00",
        "managedByPlugin": true,
        "triggeredAt": null
      }
    }
  },
  "diagnostics": []
}
```

写入方式：`await papertodo.state.save(state)`。Runtime state 上限 20 MiB，正常使用远低于此。

写盘时机：每次真实变更后立即 `save`，不要攒到页面卸载。收到 `settingsChanged` 后不要原样回写。

### 8.2 幂等性

相同 Todo、相同表达式、相同解析结果，不应重复执行提醒设置。

判定键：`(paperId, todoId, expression, resolvedAt)`。四元组与状态记录一致且 Host `reminderAt` 已等于 `lastAppliedReminderAt` 时，直接跳过。

重复事件的处理原则：

- 不重新计算已经解析过的相对时间。
- 不重复调用 `todos.setReminder`。
- 不修改 Todo 正文（V1 永不写正文）。

### 8.3 事件循环控制

插件自己的操作会产生新的 Todo 事件，因此：

1. 订阅时显式声明 `excludeOwnOperations: true`。
2. 对每条 Todo 维护 `lastAppliedReminderAt` 作为状态指纹。
3. 处理前先比对状态指纹，命中即返回。
4. 处理过程串行化：同一 `(paperId, todoId)` 的在途处理不并发。

`excludeOwnOperations` 只过滤本插件的 operation，无法过滤 MCP、导入、其他插件产生的等价写入，所以第 2、3 条不能省。

### 8.4 状态冲突

以 Host 的实际 Todo 状态为准：

- 时间表达式未变化时，不覆盖用户手动设置的提醒时间。
- 表达式被删除时，只清除仍属于 NLTodo 管理的提醒（`reminderAt === lastAppliedReminderAt`）。
- 状态与 Host 不一致且无法判定归属时，降级为 `managedByPlugin: false`，并停止管理该 Todo，等待下次正文变更再重新接管。

### 8.5 诊断记录

解析失败写入 `diagnostics` 环形缓冲（上限 50 条），字段：

```json
{
  "at": "2026-11-09T17:30:00+08:00",
  "paperId": "...",
  "todoId": "...",
  "text": "询问详细信息 @in25xz",
  "reason": "invalid_unit",
  "expression": "@in25xz"
}
```

限流规则：

- 同一 `(todoId, expression, reason)` 只记一次，直到正文变化。
- 形状不合法的 `@xxx` 不记诊断（见 3.2）。

## 9. 非功能需求

### NFR-01：资源占用

插件不得通过周期性 `todos.list` 轮询检查变化。正常运行时只在事件到达时执行解析。

### NFR-02：可靠性

- 支持 PaperTodo 重启后的状态恢复。
- 不因 Body 被销毁而停止监听。
- 不依赖持续存在的可见窗口。
- 不自行维护长期提醒计时器。

### NFR-03：数据安全

- 不修改与时间表达式无关的 Todo 内容。
- 不删除用户手动创建的提醒。
- 不进行未经授权的网络请求。
- 所有 Todo 修改均通过 PaperTodo Workspace API 完成。

### NFR-04：可维护性

时间解析器与 PaperTodo API 调用逻辑解耦：解析器是纯函数，可脱离宿主单独测试。

### NFR-05：请求超时

Runtime 文档在启动阶段可能重新导航，在途请求的响应会被丢弃且 promise 不会 settle。所有宿主调用必须带超时：

| 调用 | 超时 |
|---|---|
| `todos.list` | 6s |
| `todos.setReminder` | 8s |

超时按失败处理并交给重试层，不允许让整条对账链路挂死。

### NFR-06：宿主前置依赖

`todos.setReminder` 依赖宿主的 Labs「待办提醒」实验特性。该特性关闭时返回错误码 `reminders_disabled`，此时插件不写提醒、不重试，把 `runtime.notice` 置为 `todo_reminders_disabled`。

## 10. V1 范围与非目标

### V1 必须实现

- 普通 Todo 事件监听（created / changed / deleted）。
- 时间表达式词法边界与候选过滤。
- 绝对时间计算、相对时间计算。
- 创建、修改、删除提醒。
- 启动时状态恢复与对账。
- 幂等性、事件循环控制、异常处理。
- 解析诊断记录。
- 使用 PaperTodo 内置通知。

### V1 不实现

- 完整自然语言理解（例如「明天下午吃饭前提醒我」）。
- 单个 Todo 的多个提醒时间。
- 重复提醒。
- 中文数字、口语化时间（「下午五点」「两小时后」）。
- 日历集成、自定义提醒窗口、自定义声音、系统级独立闹钟。
- Todo 正文的自动清理、改写、高亮。
- 多时区协同。
- 可见的设置界面。

## 11. 验收标准

| ID | 测试场景 | 可观察判据 |
|---|---|---|
| AC-01 | 新建 `询问详细信息 @17tomorrow` | Host 中该 Todo 的 `reminderAt` = 次日 17:00 本地时间 |
| AC-02 | 新建 `任务 @in25m` | `reminderAt` ≈ 当前时间 + 25 分钟，误差 < 5s |
| AC-03 | 将 `@17tomorrow` 改为 `@18tomorrow` | `reminderAt` 变为次日 18:00，Todo 数量不变 |
| AC-04 | 删除时间表达式 | `reminderAt` 变为 `null`，状态记录被移除 |
| AC-05 | 只改 Todo 的无关文字（保留 `@17tomorrow`） | `reminderAt` 不变；插件未调用 `todos.setReminder` |
| AC-06 | 同一事件重复投递 | `todos.setReminder` 调用计数不增加 |
| AC-07 | 重启 PaperTodo | `reminderAt` 保持原值，`@in25m` 不重新计时 |
| AC-08 | Runtime 启动时已有带标记但无提醒的 Todo | 补设提醒；`resolvedAt` 已过期的 `@in*` 不补设 |
| AC-09 | Todo 被删除 | 状态中对应条目被移除 |
| AC-10 | `@17today` 且当前已过 17:00 | 不设置提醒，诊断新增一条 `past_time` |
| AC-11 | `@17tomorrow @18tomorrow` | 不设置提醒，诊断新增一条 `ambiguous` |
| AC-12 | 用户手动改提醒时间后只改无关文字 | `reminderAt` 保持用户设定值；状态 `managedByPlugin` 置 `false` |
| AC-13 | 正文写 `a@17tomorrow.com` | 不识别，无诊断、无提醒 |
| AC-14 | 关闭 `autoStart` 设置 | hidden 纸片不再创建/恢复，Runtime 不启动，事件不再处理（不报错，属预期行为） |
| AC-15 | 正文写 `@17`（无日期后缀） | 按待定决策 D-01 处理，行为需与文档一致 |

## 12. 实施计划

### Phase 1：最小可行原型

1. 按 5.2 创建 `plugin.json` 与 `web/{index,runtime}.html`。
2. 安装到 `plugins/papertodo.nltodo/`，重启 PaperTodo。
3. 验证 hidden 纸片被创建，且 Runtime 实际启动（打日志到 state）。
4. 订阅 `todo.created`。
5. 实现 `@17tomorrow` 解析（纯函数）与最小单测。
6. 调用 `todos.setReminder`，确认 Host 中的 `reminderAt` 被写入。
7. 等待到点，验证 PaperTodo 内置提醒正常触发。

### Phase 2：完整事件处理

1. 增加 `todo.changed` 与判定表（FR-01）。
2. 增加 `todo.deleted` 状态清理。
3. 实现表达式修改、删除处理（FR-04 / FR-05）。
4. 实现幂等性与状态指纹。
5. 补全全部 7 种语法与边界规则。

### Phase 3：可靠性

## 13. 待定决策

| ID | 问题 | 结论 |
|---|---|---|
| D-01 | `@17`（无 `today`/`tomorrow` 后缀）是否等价于今天 17:00？ | **已定：不支持。** 纯数字 token 不进入候选集，静默忽略。理由：已过 17:00 时用户容易误判成明天，解析层无法区分 |
| D-02 | 表达式的 `@` 是否需要转义机制（例如正文真的要写 `@17tomorrow` 时） | 倾向不做。V1 语法过于特殊，误触概率低 |
| D-03 | 解析诊断是否需要暴露给用户 | 倾向 V1 只落 state，Phase 4 再做界面 |
